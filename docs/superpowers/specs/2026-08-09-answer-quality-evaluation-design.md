# AI 답변 품질 자동 평가 — 설계

작성일: 2026-08-09
상태: 승인됨 (구현 계획 대기)

## 배경

공공기관 챗봇이라 경영평가·성과보고에 쓸 품질 수치가 필요하다. 현재 대시보드의
"답변 성공률"은 챗봇이 스스로 붙인 `outcome` 라벨의 집계다. 파이프라인이
`answered`로 기록하면 성공으로 세므로, 실제로는 근거 없는 답변을 했어도 성공에
포함된다. 심사에서 "이 수치를 어떻게 산출했습니까"라는 질문에
"챗봇이 스스로 성공이라고 판단한 비율"이라고 답해야 하는 상태다.

실제 대화 데이터를 상위 LLM이 채점해 독립적인 품질 지표를 산출한다.

### 이미 있는 것

| 화면 | 지표 | 성격 |
|---|---|---|
| 대시보드 | 사용자 수, 대화 수, 답변 성공률, 응답시간 | 운영 |
| ROI 대시보드 | 자동 해결률, 절감 시간·비용 | 효율 |
| 품질 리포트 | 출처 없는 답변, 검색점수 낮은 질문 | 간접 |
| 대화 분석 | outcome 분포 | 자기 신고 |

LLM이 답변 품질을 채점하는 코드는 없다. 이 설계가 채우는 빈 곳이다.

### 원자료는 이미 쌓이고 있다

`chat_messages`에 평가에 필요한 것이 모두 있다. 새로 수집할 데이터는 없다.

- `content` — 답변 본문
- `normalized_query` / `rewritten_query` — 질문
- `retrieved_documents` / `selected_sources` — 검색 근거 / 실제 인용 근거
- `final_decision` / `validation_signals` / `classification_result` — 파이프라인 판단
- `user_feedback` — 👍/👎
- `latency_ms`, `input_tokens`, `output_tokens`

## 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 평가 범위 | **전수** | 실측 이용량(챗봇당 하루 약 6건)에서 전수 비용이 월 수백 원대. 표본오차 없는 편이 경영평가에 강함 |
| 실행 시점 | **야간 배치 1회** (03:00 KST) | 이용자 응답 속도에 무영향, 배치로 묶어 비용 최소 |
| 평가 모델 | **상위 모델 고정** (gpt-4.1급) | 채점이 부정확하면 통계 전체가 무너짐. 생성보다 상위 모델로 채점하는 것이 "교차 검증" 논리로 유리 |
| 채점 구조 | **단일 호출 + 규칙 선처리** | 건당 1회 호출로 최저 비용. 지표별 개별 호출은 비용 5~6배 대비 이득이 작음 |
| 화면 | **기존 품질 리포트 확장** | 메뉴를 늘리지 않고, 자기신고 수치와 AI 평가 수치를 섹션으로 구분 |
| 과거 데이터 | **관리자가 기간 골라 수동 실행** | 비용을 기관이 통제. 평가철에 직전 1년치를 몰아서 돌릴 수 있음 |

### 비용 근거

평가 1건당 입력 약 5,000토큰(인용 근거가 대부분), 출력 약 300토큰.
인용분만 전송하는 최적화를 적용하면 입력이 약 2,500토큰으로 줄어 **건당 약 9원**이다
(상위 모델 기준). 아래는 최적화 적용 후 상위 모델 단가로 계산한 값이다.

| 규모 | 월 평가 건수 | 월 비용 |
|---|---|---|
| 챗봇 1개 (하루 6건) | 180 | 약 1,600원 |
| 기관 10곳 | 1,800 | 약 16,000원 |
| 하루 100건 대형 기관 | 3,000 | 약 27,000원 |

경량 모델을 쓰면 이보다 10배 이상 저렴하지만, 채점 정확도가 통계 신뢰도를 결정하므로
상위 모델을 쓴다. 위 금액은 전수 평가 기준이며 감당 가능한 수준으로 판단했다.

단가는 모델 가격 정책에 따라 변한다. 실제 지출은 건별 토큰 기록으로 집계해
화면에서 확인한다.

### 비용 최적화

1. **인용분만 전송** — `retrieved_documents` 전체가 아니라 `selected_sources`만. 입력 토큰 40~50% 절감
2. **1회 호출로 6지표** — 지표별 호출은 6배
3. **규칙 선처리** — LLM 없이 확정되는 건은 호출하지 않음
4. **평가 결과 재사용** — 답변 캐시로 나간 동일 건은 재평가하지 않음

OpenAI Batch API(단가 50% 할인)는 **이번 범위에 넣지 않는다.** 결과 회수까지 최대
24시간이 걸려 진행률 표시와 소급 평가 UX가 복잡해지는데, 위 비용 수준에서는 그
복잡도를 감수할 이유가 없다. 대형 기관이 늘어 비용이 문제가 되면 그때 도입한다.

## 데이터 모델

새 테이블 하나. 기존 테이블 변경 없음.

```
answer_evaluations
├─ id, organization_id, chatbot_id
├─ message_id          FK chat_messages.id  (assistant 메시지, UNIQUE)
├─ session_id
├─ evaluated_at
│
├─ relevance_score        SmallInt 0~100   답변 적합성
├─ groundedness_score     SmallInt 0~100   문서 근거성
├─ context_score          SmallInt 0~100   대화 맥락 유지 (첫 턴이면 NULL)
├─ topic_drift            Boolean          주제 이탈
├─ followup_score         SmallInt 0~100   추천질문 적합성 (추천질문 없으면 NULL)
├─ needs_review           Boolean
│
├─ verdict_json           JSONB   지표별 판정 사유
├─ method                 String  'llm' | 'rule' | 'failed'
├─ evaluator_model        String
├─ prompt_version         String  'v1'
├─ input_tokens, output_tokens        ← 지출 집계의 기준(권위 있는 값)
└─ cost_usd               Numeric    ← 평가 시점 단가로 계산한 스냅샷
```

비용은 토큰을 권위 있는 값으로 두고, `cost_usd`는 평가 당시 단가로 계산한
스냅샷으로 둔다. 모델 가격이 바뀌어도 과거 집계가 흔들리지 않는다. 화면에는
원화로 환산해 표시한다.

인덱스: `(chatbot_id, evaluated_at)`, `(needs_review)`, `message_id UNIQUE`

### 설계 의도

**NULL을 적극적으로 쓴다.** 첫 턴에는 맥락 유지가 성립하지 않고, 추천질문이 없으면
적합성도 없다. 0점으로 채우면 평균이 왜곡되므로 NULL로 두고 집계에서 제외한다.

**`method`로 규칙 판정과 LLM 판정을 구분한다.** "이 96.1%는 전부 AI가 채점한 것입니까"에
정확히 답할 수 있어야 한다.

**`prompt_version`과 `evaluator_model`을 기록한다.** 채점 기준이 바뀌면 전후 수치를
그대로 비교하면 안 된다. 이걸 남기지 않으면 "작년보다 좋아진 게 아니라 기준이
느슨해진 것 아닌가"를 반증할 수 없다.

**`message_id` UNIQUE로 중복 집계를 막는다.** 소급 평가를 여러 번 눌러도 안전하다.

## 평가 실행 흐름

ARQ 크론. 기존 `sync_due_web_sources`와 같은 방식으로 `WorkerSettings.cron_jobs`에 등록.

```
매일 03:00 (컨테이너 TZ=Asia/Seoul 기준)
│
├─ ① 대상 선별
│    전날 assistant 메시지 중 아래를 제외
│    · is_test = True
│    · 이미 평가된 message_id
│    · 인사·스몰토크 (simpleResponseApplied)
│    · 답변 캐시 히트
│    · outcome이 answered 가 아닌 건
│      (insufficient_evidence · escalate · restricted)
│
├─ ② 규칙 선판정 (LLM 없이 확정)
│    · outcome=answered 인데 인용 0개 → groundedness=0, needs_review=true
│    · out_of_scope 판정            → topic_drift=true
│    · 추천질문 없음                 → followup_score=NULL
│    · FAQ 경로                     → groundedness=100 (등록 답변 자체가 근거)
│
├─ ③ LLM 채점 (남은 건, 건당 1회)
│    입력: 질문 + 답변 + selected_sources + 직전 대화 1턴
│    출력: 지표별 [사유 → 점수] JSON
│
└─ ④ 저장 + 비용 누적
```

### 선별 규칙의 근거

**`answered`가 아닌 건은 평가 대상에서 뺀다.** 근거가 없어 "자료에서 확인하기
어렵습니다"라고 정직하게 답한 건(`insufficient_evidence`)을 품질 미달로 세면,
챗봇이 모르는 것을 아는 척할수록 점수가 올라가는 지표가 된다. 이관(`escalate`)과
정책 차단(`restricted`)도 답변 품질을 논할 대상이 아니다. 이들은 품질이 아니라
**지식 커버리지 / 운영 지표**이므로 섹션 1에서 따로 센다.

**FAQ 경로도 평가한다.** 근거성은 규칙으로 100이지만 적합성은 반드시 봐야 한다.
"거주자주차를 물었는데 정기주차 FAQ가 매칭되는" 유형의 오류가 여기서 잡힌다.

### 소급 평가

같은 함수를 기간 인자만 바꿔 호출한다. 관리자가 품질 리포트에서 기간을 지정하면
대상 건수와 예상 비용을 먼저 보여주고, 확인받은 뒤 ARQ에 넣는다. 진행률을 표시하고
완료되면 그래프에 반영된다. 이미 평가된 건은 `message_id` UNIQUE로 자동 건너뛴다.

## 지표 정의와 산출식

### 채점 척도

0~100점, **70점이 기준선**.

| 구간 | 의미 |
|---|---|
| 90~100 | 근거·질문에 정확히 부합 |
| 70~89 | 요구를 충족하나 개선 여지 |
| 40~69 | 부분적으로 어긋남 |
| 0~39 | 부적합 |

### 표시값은 평균이 아니라 충족률

**"70점 이상을 받은 비율"** 을 주 지표로 표시하고, 평균 점수를 보조로 함께 둔다.

평균을 쓰면 꼬리가 숨는다. 90%가 100점이고 10%가 42점이면 평균 94.2로 훌륭해
보이지만 열 건 중 하나가 불량이다. 충족률은 이를 드러낸다.

집계 시 NULL은 분모에서 제외한다. 표본이 0건이면 0%가 아니라 "데이터 없음"으로
표시한다.

### 지표 목록

| 지표 | 채점 기준 | 표시 |
|---|---|---|
| 답변 적합성 | 질문이 요구한 것에 실제로 답했는가 | 충족률 % |
| 문서 근거성 | 답변의 각 진술이 인용 근거로 뒷받침되는가 | 충족률 % |
| 대화 맥락 유지 | 앞 대화를 올바로 이어받았는가 (첫 턴 제외) | 충족률 % |
| 주제 이탈 | 기관 업무 범위를 벗어났는가 | 발생 비율 % (낮을수록 좋음) |
| 추천질문 적합성 | 제시한 후속 질문이 맥락에 맞는가 | 충족률 % |
| 검토 필요 | 근거성 or 적합성 70 미만, 또는 주제 이탈 | 건수 |

### 임계값을 기관별 설정으로 두지 않는 이유

평가 모델을 고정하는 것과 같은 이유다. 기관마다 기준선이 다르면 "A기관 95%가
B기관 88%보다 낫다"가 성립하지 않고, 한 기관 안에서도 임계값을 낮추면 점수가
올라가므로 연도 간 비교가 무너진다. 70점 고정으로 모든 기관·연도가 같은 자를 쓴다.

### 프롬프트 설계

단일 호출로 6지표를 채점하면 점수가 서로 끌려가는 halo effect가 생긴다.
**각 지표마다 판정 사유를 먼저 쓰고 점수를 나중에 매기도록** 출력 순서를 강제해
이를 억제한다.

```
{ "relevance":    { "reason": "...", "score": 0-100 },
  "groundedness": { "reason": "...", "score": 0-100 },
  ... }
```

## 화면 (품질 리포트 확장)

### 섹션 1 — 운영 지표 (기존 유지)

총 대화 수 · 답변 성공률 · 평균 응답시간 · 출처 없는 답변.
**"챗봇 자체 판정 기준"** 안내를 달아 아래 AI 평가 수치와 성격이 다름을 명시한다.
없으면 "성공률 82.77%인데 적합성은 94.2%? 뭐가 맞나"라는 혼동이 생긴다.

### 섹션 2 — AI 답변 품질 (신규)

```
AI 답변 품질                     전수 평가 · gpt-4.1 · 기준 v1
                                2026-07-01 ~ 2026-07-31 · n=1,842

┌─────────────┬─────────────┬──────────────┐
│ 답변 적합성  │ 문서 근거성  │ 대화 맥락 유지 │
│  94.2% ⓘ    │  96.1% ⓘ    │  92.8% ⓘ      │
│ 평균 88.4점  │ 평균 91.2점  │ 평균 85.9점    │
│ ▲ 1.8%p     │ ▼ 0.4%p     │ ▲ 3.1%p       │
└─────────────┴─────────────┴──────────────┘
┌─────────────┬─────────────┬──────────────┐
│ 주제 이탈    │ 추천질문적합성│ 검토 필요      │
│  2.1% ⓘ     │  91.5% ⓘ    │  18건 →       │
└─────────────┴─────────────┴──────────────┘

일별 추이 (적합성 · 근거성 · 맥락)

판정 구성: AI 채점 1,720건 · 규칙 확정 122건 · 실패 0건
```

전월 대비 증감을 카드에 표시한다. 경영평가는 항상 전기 대비를 묻는다.

신뢰를 위해 함께 노출하는 것:
- 표본 수 (`n=1,842`)
- 평가 방식 (전수 여부 · 모델 · 기준 버전)
- 지표별 ⓘ — 정의와 기준선
- AI 판정 / 규칙 판정 / 실패 건수 구성

### 검토 필요 목록

통계만으로는 개선으로 이어지지 않는다. 운영 가치는 이 목록에 있다.

| 일시 | 질문 | 미달 지표 | 판정 사유 | |
|---|---|---|---|---|
| 08-05 14:22 | 거주자주차 이용요금 | 적합성 32 | 정기주차 요금을 안내함 | 대화 보기 |
| 08-05 09:11 | 신청 서류 | 근거성 41 | 근거에 없는 제출처를 언급 | 대화 보기 |

판정 사유를 그대로 노출한다. 담당자가 판단하려면 필수이고, 심사에서 표본 검증을
요구할 때 이 화면을 제시할 수 있다.

## 오류 처리와 안전장치

### 이벤트 루프 차단 방지

2026-07-31 API 정지의 원인이 동기 블로킹 코드를 async 핸들러에서 호출한 것이었다.
평가 작업도 같은 위험이 있다 — LLM 클라이언트가 동기인데 워커는 async다.

```python
async def evaluate_answers(ctx, ...):
    await asyncio.to_thread(_run_evaluation_batch, ...)
```

기존 `sync_due_web_sources`가 쓰는 패턴을 그대로 따른다. 워커가 막히면 색인 작업까지
멈추므로 양보할 수 없다.

### 실패 처리

| 상황 | 처리 |
|---|---|
| LLM 타임아웃·네트워크 오류 | 3회 재시도 → `method='failed'` |
| JSON 파싱 실패 | 1회 재요청 → 실패 시 `method='failed'` |
| 일부 지표만 누락 | 있는 것만 저장, 나머지 NULL |
| 배치 중간 중단 | 건별 커밋이라 재실행 시 이어서 진행 |

실패 건수를 화면에 표시한다. 실패를 숨기면 표본 수가 조용히 줄어 통계가 왜곡된다.

### 비용 안전장치

- 소급 평가는 예상 비용 확인 후 실행
- 건별 토큰·비용 기록 → 실제 지출을 화면에서 확인
- 상한 도달 시 로그 경고 + 관리자 알림

## 테스트

LLM 호출은 모킹한다. 순수 함수 단위 테스트가 이 프로젝트의 패턴이다.

| 대상 | 검증 내용 |
|---|---|
| 대상 선별 | 테스트·인사말·캐시히트·답변못함이 제외되는지 |
| 규칙 선판정 | 인용 0개 → 0, FAQ → 100, 추천질문 없음 → NULL |
| 응답 파싱 | 정상 JSON / 깨진 JSON / 일부 필드 누락 |
| 충족률 산출 | NULL이 분모에서 빠지는지, 표본 0건이 "데이터 없음"인지 |
| 임계값 | 69 · 70 · 71 경계 |
| 중복 방지 | 같은 message_id 재평가 시 건너뛰는지 |

충족률 산출과 NULL 처리가 가장 중요하다. 여기가 틀리면 숫자 전체가 틀린다.
